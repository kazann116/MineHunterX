# MineHunter X — архитектура (MVP, этапы 0–6)

## Слои

```
MineHunter.App (VCL)            — формы, модели представления, composition root (Bootstrap)
        │ использует
MineHunter.Core                 — модели, контракты, DI, сканер, настройки, отчёты, действия
        │ реализуют контракты
Collectors / Analysis / Storage — независимые провайдеры
```

Core не зависит от VCL. Приложение получает сервисы через `TMHAppServices`
и не знает, какие именно коллекторы подключены. Подробный перечень типов — в [api.md](api.md),
модель угроз — в [threat-model.md](threat-model.md), ограничения — в [limitations.md](limitations.md).

## Поток данных одного цикла

```
Коллекторы (system → processes → autostart → network → files → context → self)
   │  TMHCollectionResult: статус + данные (снимок не мутируется, сбой изолирован)
   ▼
Сканер: объединение, обогащение процессов (подпись/хеш из files, командная строка
        и окна из context), запись снимка в SQLite (статус источника «storage»)
   ▼
Анализатор угроз (скользящее окно нагрузки, реакция на диспетчер задач,
        правила с весами, профиль нормы контекста) → TMHFindings → история находок
   ▼
События: OnSnapshot / OnFinding / OnCycle → главный поток (очередь, отмена после Stop)
   ▼
UI: обзор, процессы (риск/подпись), находки и карточка, история и сравнение с нормой, настройки
```

Фоновые службы: перестроение профиля нормы раз в час (`TMHBaselineScheduler`, первый раз —
через минуту после запуска), проверка Microsoft Defender и загрузка истории — в отдельных потоках
с отменой при закрытии окна. Перестроение читает период обучения десятью порциями по времени
(`TMHBaselineAccumulator`), поэтому в памяти одновременно находится выборка только одной порции.

Ограничение памяти: история нагрузки в анализаторе — не чаще одной точки на процесс за 2 с
(окно не зависит от интервала опроса); кэш страниц SQLite — 2000 страниц (≈ 8 МБ) вместо 10000
по умолчанию в FireDAC.

## Анализатор угроз (этапы 3–5)

`MineHunter.Analysis.Engine.TMHThreatAnalyzer` — версия правил `MH_RULESET_VERSION`,
база индикаторов `MineHunter.Analysis.Indicators` (`MH_INDICATORS_VERSION`).

- Длительная нагрузка: средняя за `SustainedMinutes` ≥ `HighCpuPercent` машины или
  ≥ `HighCoreCpuPercent` одного ядра, при покрытии окна данными ≥ 90%.
- Сеть: порт пула учитывается только вместе с нагрузкой или другими признаками майнинга.
- Подпись: отсутствие подписи даёт лишь +10; доверенная подпись — оправдывающий фактор,
  кроме случаев, когда угроза в аргументах команды (закодированный PowerShell).
- Контекст: активное окно, полноэкранный режим, бездействие пользователя, известные
  ресурсоёмкие задачи (сборка, рендеринг, обновления, антивирус, игры, браузеры) — только
  при обычном расположении и подписи файла.
- Норма: отклонение выше p95 профиля текущего контекста повышает оценку, обычная для
  компьютера нагрузка снижает её.
- Автозапуск: необычное расположение, сценарии вне системных папок, папки со случайными
  именами, задания, замаскированные под системные, скрытые/закодированные команды.
- Системная перегрузка CPU/памяти/диска объясняется находкой «необычная нагрузка» с
  перечнем основных потребителей.
- Уверенность снижается при нехватке данных (нет прав, подпись не проверена, короткая
  история, профиль нормы не сформирован); недостающее перечисляется в находке.

Качество проверяется 23 синтетическими сценариями (8 имитаций угроз и 15 легальных нагрузок)
и сохранёнными обезличенными фикстурами `tests/Fixtures/regression/*.jsonl`; отчёт —
[false-positive-report.md](false-positive-report.md).

## Публичный API (контракт MVP)

| Тип | Модуль | Назначение |
|---|---|---|
| `TMHProcessId` | `MineHunter.Core.Types` | Идентичность экземпляра процесса: PID + время создания (FILETIME). PID переиспользуется Windows, поэтому одного PID недостаточно. |
| `TMHProcessInfo` | там же | PPID, путь, хеш, подпись, уровень доступа, CPU/RAM, потоки, источник данных. |
| `TMHMetric` | там же | Измерение; `HasValue = False` означает «нет данных», а не ноль. |
| `TMHSourceStatus` | там же | Статус источника: `ssSuccess / ssPartial / ssUnavailable / ssError` + пояснение и признак необходимости повышенных прав. |
| `TMHEvidence`, `TMHFinding` | там же | Признаки (положительные и отрицательные), балл 0–100, уровень, уверенность, недостающие данные, версия правил. |
| `TMHRiskThresholds` | там же | Настраиваемые пороги перевода балла в уровень. Уровни описывают степень подозрения, а не диагноз. |
| `TMHSnapshot` | там же | Состояние системы на момент опроса. |
| `IMHCollector.Collect(Snapshot): TMHCollectionResult` | `MineHunter.Core.Interfaces` | Единый контракт сбора. |
| `IMHAnalyzer.Analyze(Snapshot, Baseline): TMHFindings` | там же | Детерминированный анализ. |
| `IMHRepository.SaveSnapshot / LoadHistory` | там же | Хранение истории без привязки к GUI. |
| `IMHClock`, `IMHLogger`, `IMHLogReader` | там же | Время (для детерминированных тестов) и журнал. |
| `TMHScanner` | `MineHunter.Core.Scanner` | `Start / Stop / ScanOnce / OnSnapshot / OnFinding`. |
| `TMHContainer` | `MineHunter.Core.Container` | DI: singleton / transient / instance, `ResolveAll` для коллекторов, обнаружение циклов. |

### Решение по контракту `Collect`

В ТЗ сигнатура `Collect(Snapshot): TMHCollectionResult` допускает два толкования.
Принято следующее: коллектор **не изменяет** снимок. Он получает снимок
текущего цикла только для чтения и возвращает свои данные вместе со статусом.
Сканер объединяет результат со снимком, только если коллектор завершился без
исключения. Поэтому сбой одного источника не может оставить снимок в
полузаполненном состоянии.

## Сканер и потоки

- Один фоновый поток `TMHScanner.TWorker`; циклы сериализуются `FScanLock`,
  поэтому `ScanOnce` безопасен и при запущенном потоке.
- Интервал опроса — от 250 мс до 10 мин; между циклами всегда есть пауза
  не меньше 100 мс, даже если источник медленный.
- Изоляция сбоев: исключение коллектора даёт статус `ssError`, остальные источники
  продолжают работать. После `MaxConsecutiveFailures` ошибок подряд источник
  отключается на 1, 2, 4… циклов (не более `MaxBackoffCycles`), затем опрос
  возобновляется автоматически.
- Исключения анализатора и обработчиков событий записываются в журнал и не
  останавливают сканирование.
- Доставка событий:
  - `edMainThread` (по умолчанию) — через `TThread.Queue`. У каждого запуска своя
    эпоха; `Stop` меняет её до ожидания потока. Поэтому события, оставшиеся в очереди,
    не доходят до обработчиков даже тогда, когда `TThread.WaitFor` сам обрабатывает
    очередь синхронизации. Остатки удаляет `RemoveQueuedEvents` при уничтожении потока.
  - `edWorkerThread` — прямо в потоке сканера (для служб и тестов).
- `Start/Stop/Free` вызываются из главного потока. В обработчиках нельзя
  вызывать `Stop` и `TThread.Synchronize`.

## DI

Composition root — `TMHAppServices.RegisterDefaults`. Тесты собирают свой
контейнер с тестовыми двойниками (`tests/Fixtures`) и передают его в
`TMHAppServices.Create` / `TMainForm.CreateWithServices`.

## Коллекторы

| SourceId | Модуль | Данные |
|---|---|---|
| `system` | `MineHunter.Collectors.System` (+ `.WinApi`) | Загруженность CPU как в диспетчере задач (`% Processor Utility`), время работы (`GetSystemTimes`, `mkCpuTimePercent`), частота относительно базовой и предел производительности (троттлинг), память (`GlobalMemoryStatusEx`, точная доля), диск: чтение/запись, активность самого загруженного физического диска, сеть. PDH через `MineHunter.Collectors.Pdh` (`PdhAddEnglishCounterW` — имена не зависят от языка Windows; счётчики независимы). |
| `gpu` | `MineHunter.Collectors.Gpu` (+ `.WinApi`) | Счётчики `GPU Engine`, `GPU Process Memory`, `GPU Adapter Memory`: загрузка процесса — его самый загруженный движок, вычисления — движки Compute/CUDA, видеопамять; температура и порог снижения частоты — D3DKMT (`KMTQAITYPE_ADAPTERPERFDATA`), затем NVML (только из System32 / NVSMI). Сведения о процессах — через `ProcessDetails`, поэтому коллектор стоит после `processes`. |
| `sensors` | `MineHunter.Collectors.Sensors` (+ `.WinApi`) | Температура накопителей (`IOCTL_STORAGE_QUERY_PROPERTY`, `StorageDeviceTemperatureProperty`, без прав администратора; раз в минуту) и процессора из LibreHardwareMonitor/OpenHardwareMonitor (WMI, если запущены; раз в 10 с). |
| `processes` | `MineHunter.Collectors.Processes` (+ `.WinApi`) | Все процессы: PID + время создания, PPID, имя, путь, CPU (дельта), рабочий набор, частная память, потоки, уровень доступа. |
| `self` | `MineHunter.Collectors.SelfMonitor` | CPU, рабочий набор и приватная память самого MineHunter — для контроля требований «≤ 2% CPU» и «≤ 200 МБ». Первый замер — `ssPartial`: CPU считается по разнице двух замеров. |

### Коллектор процессов (этап 1)

- Перечень — `CreateToolhelp32Snapshot`. Сведения — через `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`,
  `GetProcessTimes`, `QueryFullProcessImageNameW`, `GetProcessMemoryInfo`. `SeDebugPrivilege` не включается.
- Доступ: `alFull` — всё получено; `alLimited` — процесс открыт, но части полей нет (например, PID 0, `System`);
  `alDenied` — открыть не удалось. Недоступные процессы не скрываются: из перечня известны имя, PPID и число потоков.
- Статус `ssPartial`, если есть `alDenied`/`alLimited`; `RequiresElevation` — только если программа не запущена
  от имени администратора.
- CPU считается по дельте для одного и того же экземпляра (PID + время создания). Новый экземпляр с
  переиспользованным PID и уменьшившиеся счётчики дают «нет данных», а не мусорное значение.
- Гонки: процесс, завершившийся между перечислением и открытием, пропускается (`pqGone`). Если имя из перечня
  не совпадает с образом по открытому дескриптору (PID уже переиспользован), запись тоже пропускается: данные
  другого процесса не приписываются чужому имени.
- Замеры CPU хранятся только для живых экземпляров, поэтому словарь не растёт.
- Системные вызовы скрыты за `IMHProcessApi`; все сценарии отказов проверяются детерминированно
  (`tests/Fixtures/MineHunter.Tests.FakeProcessApi.pas`).
- Хеш SHA-256 и цифровая подпись (MH-01) добавляются инспектором файлов (`files`) и переносятся в записи процессов сканером.

Правило снимка: системная метрика каждого вида — одна на снимок (её читают UI и хранилище).
При конфликте источников используется значение первого по порядку регистрации, конфликт журналируется.

## Хранилище истории (этап 2)

`MineHunter.Storage.SQLite` — `TMHSQLiteRepository` реализует `IMHRepository` и `IMHMetricHistory`.

- FireDAC со статически встроенным SQLite (`FireDAC.Phys.SQLiteWrapper.Stat`): `sqlite3.dll` не нужна.
- Файл: `%LOCALAPPDATA%\MineHunterX\history.db` (каталог профиля пользователя — доступ только у пользователя).
- Целостность: WAL, `synchronous=NORMAL`, транзакция на снимок, `PRAGMA quick_check` при открытии. Повреждённый
  файл переименовывается в `history.db.corrupt-<время>` (вместе с `-wal`/`-shm`) и создаётся новая база.
- Миграции: таблица `schema_version`; база более новой версии не изменяется (ошибка открытия).
- Объём: системные метрики каждого снимка + не более `MaxProcessesPerSnapshot` (30) самых нагруженных процессов.
- Ротация (каждые 300 сохранений и при открытии): удаление старше `RetentionDays` (7), затем самых старых при
  превышении `MaxDatabaseBytes` (256 МБ); `incremental_vacuum` возвращает место.
- Приватность: `StoreProcessPaths = False` — пути процессов не записываются.
- Ряды для графиков: усреднение по интервалам в SQL (`GROUP BY`), `NULL` → «нет данных».
- Типы: 64-битные колонки объявлены `BIGINT` (FireDAC читает `INTEGER` как 32-битное); числа из выражений
  (`AVG`) читаются без зависимости от локали.
- Сканер сохраняет снимок в своём потоке; сбой записи даёт статус источника `storage = ошибка` и не
  останавливает мониторинг. Если база не открылась, приложение работает без истории и показывает причину.

## UI

- «Обзор»: живые графики CPU, памяти и активности диска (кольцевой буфер 300 точек), текстовая сводка,
  частота и троттлинг процессора, сеть, видеокарта (вычисления, видеопамять), температуры;
  четвёртый живой график — видеокарта. Страница «Обзор» построена из модели
  `MineHunter.App.DashboardView` (чистые функции: карточки «Сейчас» с состоянием
  норма/внимание/высокая и упорядоченный список причин с итогом первой строкой) и элементов
  `MineHunter.App.Tiles` (`TMHMetricTile`, `TMHReasonList`; состояние передаётся цветом, словом
  и значком). Источники данных, журнал и самодиагностика — во вкладках «Подробности». На странице «Процессы» колонки «Память» (частный
  рабочий набор) и «GPU», как в диспетчере задач.
- «История»: 5 графиков за 1 ч / 6 ч / 24 ч / 7 дней; загрузка в фоновом потоке (одновременно один загрузчик,
  результат доставляется через очередь потока и отменяется при закрытии формы).
- «Обзор»: блок «Состояние защиты» — число тревог текстом, «почему компьютер может тормозить»,
  права и недоступные источники.
- «Находки»: активные тревоги и история за 7 дней, фильтр по уровню; карточка с признаками «за/против»,
  недостающими данными, рекомендациями, графиком нагрузки процесса за час и действиями
  (открыть расположение, Defender, остановить процесс, «это моя программа», экспорт JSON/HTML).
- «История»: сравнение выбранного периода с профилем нормы текущего контекста и список программ,
  отклонившихся от нормы; кнопка перестроения профиля.
- «Настройки»: интервал, хранение и приватность, пороги анализа, период обучения, автозапуск
  сканирования, обезличивание отчётов, разрешённые программы, журнал действий. Настройки
  сохраняются атомарно в `%LOCALAPPDATA%\MineHunterX\settings.json`.
- `MineHunter.App.Chart` — собственный график без внешних зависимостей: разрывы на «нет данных» и паузах,
  масштабирование по DPI, `SummaryText`/подсказка дублируют график текстом.

## Вспомогательные модули Core

- `MineHunter.Core.Paths` — нормализация путей (`\?\`, `\??\`, `/`, `..`, `\SystemRoot\`) и сравнение
  `MHSamePath`, чтобы подмена формы пути не обходила проверки.
- `MineHunter.Core.Serialization` — JSON (`TMHJson`): время в ISO 8601 UTC, FILETIME строкой (без потери
  точности > 2^53), «нет данных» — `null`, версия формата `schema`. При ошибочном входе — `EMHSerializationError`.

## UI: страница «Процессы»

Виртуальный `TListView` (`OwnerData`) поверх `TMHProcessListModel` (`MineHunter.App.ProcessView`):
- сортировка по клику на заголовок (▲/▼); «нет данных» всегда в конце;
- фильтр по имени, части пути или точному PID;
- выбор привязан к идентичности процесса и сохраняется при пересортировке; о завершившемся процессе
  выводится сообщение;
- в подробностях — родитель (с проверкой, что «родитель» не появился позже потомка, то есть PID не
  переиспользован), путь, метрики, уровень доступа и пояснение, что нехватка прав — не признак угрозы;
- сбой источника не очищает таблицу: остаются последние известные данные.

## Ограничения сборки и тестов

- Температура процессора без драйвера ядра недоступна (используется LibreHardwareMonitor, если
  запущен); пороги температуры — от производителя или консервативные (см. limitations.md).
- Снимок содержит показания датчиков (`TMHSnapshot.Sensors`: устройство, температура, порог).
  Анализатор строит по ним системные находки «перегрев» (температура держится на пороге
  устройства весь интервал) и «троттлинг» (предел производительности ниже 90%), а также причины
  в `MHExplainLoad` (`heat:gpu`, `heat:disk`, `heat:cpu`, `throttle`, `gpu`).
- Правила GPU (MH-2026.10.2): `GPU_SUSTAINED` (средняя загрузка GPU ≥ 40% за интервал, +20),
  `GPU_COMPUTE_BACKGROUND` (вычисления ≥ 30% у фонового процесса без окна, +25); вместе с
  неподписанным файлом или другим признаком угрозы — категория «майнинг».
- CI-workflow рассчитан на self-hosted Windows-раннер с RAD Studio 12:
  на GitHub-hosted раннерах Delphi нет.
- Проверка утечек в тестах сравнивает размер кучи RTL до и после многократных
  циклов работы сканера; утечки дескрипторов проверяются отдельными интеграционными тестами
  коллекторов и soak-тестом (`tests/Soak`).
